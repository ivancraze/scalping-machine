# Рекомендации по развитию Pulse Terminal и работе с ИИ

## Срез проекта относительно целей

| Направление        | Состояние                      | Что делать дальше                                                                  |
| ------------------ | ------------------------------ | ---------------------------------------------------------------------------------- |
| Личный скринер     | Есть базовый терминал          | Укрепить сценарии наблюдения, сохранение настроек и сигналы                        |
| Список рынка       | Есть поиск и сортировки        | Вынести в widget/features, добавить фильтры и настоящие futures-источники          |
| Один график        | Есть свечи, объём и line-tools | Сохранение разметки, индикаторы, WebSocket, история                                |
| Telegram-сигналы   | Спроектированы в TODO          | Нужен backend и безопасное хранение токена бота                                    |
| Поиск формаций     | Только цель                    | Начать с rule-based алгоритмов и исторических тестов                               |
| Сетка графиков     | Только цель                    | Нужны кэш, подписки, виртуализация и лимит активных тайлов                         |
| Мультибиржевость   | Только Binance Spot REST       | Ввести exchange-adapter, затем Bybit и OKX                                         |
| FSD                | Частичная миграция             | Реально разнести market list и действия пользователя по слоям                      |
| Производительность | MVP работает                   | Убрать burst-запросы корреляции, lazy-load line-tools, перейти к `series.update()` |

## Рекомендуемый порядок работ

Не пытаться строить все направления одновременно. Оптимальный порядок:

1. **Стабилизировать базовый график.** Сохранение объектов, корректная загрузка истории, индикаторы и устранение неявных UI-багов.
2. **Выделить market-data слой.** Нормализованные контракты для ticker/candle/order book, Binance Futures вместо Spot там, где это заявлено.
3. **Сделать минимальный backend наблюдения.** Предпочтительно NestJS: WebSocket-коллектор, хранение короткой истории, Telegram-сервис и API для фронтенда.
4. **Собрать сетку графиков.** Только после появления кэша, подписок и ограничителей производительности.
5. **Добавить rule-based формации.** Сначала несколько прозрачных стратегий с проверяемыми параметрами и backtest-наблюдением.
6. **Расширить на Bybit и OKX.** Когда contracts и адаптер Binance станут устойчивыми.

## Как эффективно ставить задачи ИИ

Лучший формат — одна конкретная задача, с ожидаемым результатом и границами. Хороший запрос:

> Вынеси market list из страницы в `widgets/market-list`. Сохрани текущие сортировки и поиск. Не меняй API-логику. Добавь тест или ручной сценарий проверки. После изменений запусти `npm run check`.

Плохой запрос:

> Сделай всё красиво и быстро.

Для сложной задачи полезно сразу указать:

- что именно должно измениться для пользователя;
- файлы или слой, который можно менять;
- что нельзя менять;
- источник данных и допустимые допущения;
- критерии готовности: тесты, screenshot, производительность, документация.

## Роли агентов и когда их включать

### 1. Основной implementation agent

Ведёт текущую задачу: читает существующий код, предлагает/вносит ограниченные изменения, проверяет их и сообщает результат. Он должен соблюдать `AGENTS.md`.

Использовать для UI, FSD-миграции, небольших API-изменений, документации и связанных задач.

### 2. Performance Code Reviewer

Подключать после каждого крупного изменения. Он особенно нужен перед:

- переходом на WebSocket;
- внедрением сетки 4×4 и больше;
- подключением новой библиотеки;
- появлением кэша/воркеров/фоновых задач;
- крупной FSD-миграцией.

Его результат должен быть списком P0/P1/P2, а исправления делает основной агент отдельным шагом.

### 3. Architecture/FSD reviewer

Нужен, когда файлов становится заметно больше. Его задача — не дизайн, а ясные границы: `shared` не зависит от бизнес-слоёв, страницы не превращаются в монолиты, а импорты идут через публичные API.

### 4. Market-data engineer

Использовать для проектирования backend и интеграции бирж. Отдельно проверяет:

- spot/futures контракты;
- символы и нормализацию;
- reconnect, gap recovery и rate limits;
- историю и агрегирование секундных свечей;
- данные стакана, OI и funding.

### 5. Pattern-research agent

Использовать только после появления качественной истории. Он переводит субъективные названия сетапов в формулы и тестируемые правила. Его результат — спецификация алгоритма, набор параметров, примеры срабатываний и антипримеры; не «магический детектор формаций».

### 6. QA agent

Нужен до выхода Telegram-сигналов и после появления backend. Поддерживает сценарии:

- выбор пары и сортировки;
- создание, перемещение, удаление и восстановление объектов;
- события цены и защита от повторных Telegram-сообщений;
- восстановление после разрыва WebSocket;
- корректность разметки на разных таймфреймах и биржах.

### 7. Security reviewer

Обязателен перед хранением Telegram-токена, настройкой аккаунтов, доступов и backend-деплоем. Главная задача — ни один секрет не должен попасть во фронтенд или репозиторий.

## MCP и инструменты: лучшие практики

Использовать только те интеграции, которые реально нужны текущей задаче.

| Инструмент / MCP            | Когда применять                                            | Правило                                                                           |
| --------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Файловая система и терминал | код, тесты, линтинг, сборка                                | изменения через patch; не удалять чужие файлы и не делать destructive git-команды |
| Browser / локальный браузер | проверка интерактивного UI, графика, меню, скриншоты       | тестировать кликами реальные сценарии, не ограничиваться build                    |
| Web                         | актуальная документация бирж, библиотек, лицензий, лимитов | опираться на официальную документацию и ссылаться на источник                     |
| GitHub                      | API line-tools, issues, примеры использования              | проверять лицензию и версию перед включением в production                         |
| Code review agent           | крупные изменения                                          | не просить его переписывать код без отдельной задачи                              |
| Automation                  | регулярная проверка данных, напоминания, мониторинг        | применять только для явно запрошенных повторяющихся задач                         |

Для Binance, Bybit, OKX и Telegram предпочтительнее сначала использовать официальные REST/WebSocket API через собственный backend. Плагины или сторонние MCP не должны становиться единственной точкой доступа к рыночным данным.

## Практика работы с нейросетями над формациями

Нейросеть полезна не как «глаз, который угадал паттерн», а как помощник в цикле исследования:

1. Описать стратегию человеческим языком.
2. Попросить ИИ предложить измеримые правила и спорные места.
3. Согласовать формальную спецификацию: входные свечи, уровни, допуски, подтверждение, invalidation.
4. Реализовать детерминированный алгоритм.
5. Прогнать его на истории и сохранить кандидаты.
6. Разметить вручную удачные/ложные случаи.
7. Уточнить правила или только затем рассматривать ML-модель.

Такой подход делает результаты проверяемыми и объяснимыми: у каждой найденной формации можно показать, по каким условиям она была выбрана.

## Минимальный набор инженерных практик

- Каждый существенный экран или feature получает понятную ответственность и публичный API.
- Перед merge: `npm run check`.
- Перед крупным merge: performance review и ручной UI-smoke test.
- Внешние API скрываются за адаптерами и контрактами, а не вызываются из множества компонентов.
- Изменения данных и визуализации измеряются: размер bundle, число запросов, время отрисовки, число активных WebSocket-подписок.
- Секреты — только в backend environment variables.
- README, TODO и PROJECT_GOALS обновляются при изменении направления проекта.
