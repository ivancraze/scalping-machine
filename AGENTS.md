# Правила для ИИ-агентов Pulse Terminal

Этот файл обязателен для любого ИИ-агента, который анализирует, меняет или проверяет проект.

## Контекст проекта

Pulse Terminal — личный крипто-скринер для наблюдения за рынком. Проект не должен выполнять торговые операции, выставлять ордера, запрашивать или хранить API-ключи пользователя для трейдинга.

Основные продуктовые цели описаны в [PROJECT_GOALS.md](./PROJECT_GOALS.md), ближайшие задачи — в [TODO.md](./TODO.md), фактическое состояние — в [README.md](./README.md).
Для работы на другом компьютере или в новом чате сначала прочитать [PROJECT_CONTEXT.md](./PROJECT_CONTEXT.md).

## Что разрешено и что запрещено

- Можно использовать публичные рыночные данные, WebSocket-потоки и backend-сервисы наблюдения.
- Нельзя добавлять исполнение сделок, управление балансом, хранение торговых ключей или любые скрытые торговые действия.
- Нельзя копировать код, бренд, логотипы, закрытые данные или визуальные ассеты сторонних скринеров. Референсы Digash, Scalpx и других сервисов — только ориентир по классу интерфейса и сценариям.
- Не выдавать режимы 1с/5с/15с за реальные, пока данные не агрегируются из потока сделок или не поступают от соответствующего источника.
- Не называть Spot-данные Futures-данными. Рынок, биржа, задержка и источник метрики должны быть честно обозначены в UI и коде.

## Архитектура и код

Проект использует Feature-Sliced Design. Миграция ещё продолжается, но новые изменения должны идти в правильный слой:

```text
app/       # инициализация и композиция приложения
pages/     # экран и пользовательский сценарий
widgets/   # крупные самостоятельные блоки UI
features/  # действия пользователя: поиск, сортировка, выбор символа, алерты
entities/  # рыночные модели, DTO, вычисления предметной области
shared/    # инфраструктура: HTTP, конфиг, базовые утилиты, UI-примитивы
```

- Не создавать папки-заглушки и re-export-файлы без реального переноса реализации.
- `shared` не должен импортировать `entities`, `features`, `widgets` или `pages`.
- Не импортировать реализации через глубокие пути, когда есть публичный `index.ts` слоя.
- Выносить новый крупный UI-блок из страницы в `widgets`; действия пользователя — в `features`.
- Хранить SCSS Module рядом с владельцем компонента. В `src/styles.scss` допускаются только reset и глобальные базовые стили.
- Использовать TypeScript строго, не маскировать несовместимости библиотек необоснованными `any`/опасными cast. Если сторонняя библиотека имеет дефект типов, изолировать адаптер и документировать причину.
- Не пересоздавать график при обновлении данных. Для live-обновлений использовать инкрементальные обновления series и сохранять масштаб пользователя.

## Работа с графиком и line-tools

- Ручные объекты должны быть нативными line-tools, привязанными ко времени и цене свечей, а не SVG-слоем поверх canvas.
- При изменении объектов предусмотреть сохранение и восстановление через `exportLineTools()` / `importLineTools()`.
- Любой автоматически созданный уровень или формация должны отличаться от ручной разметки и иметь понятное происхождение.
- При удалении объектов не затрагивать другие объекты или данные графика.
- `MarketDepth` нельзя считать реализованным, пока он не получает реальные агрегированные данные стакана.

## Данные, сеть и производительность

- Перед созданием многочисленных запросов проверить кэш, отмену предыдущих запросов и ограничение параллелизма.
- Для рынков и графиков предпочитать WebSocket REST-поллингу, когда появится backend.
- Не выполнять тяжёлый расчёт формаций или корреляций на главном потоке при больших выборках: использовать Web Worker или серверную обработку.
- Не загружать тяжёлые инструменты графика в стартовый bundle без необходимости. Использовать lazy/dynamic import по первому применению.
- Следить за размером production bundle, виртуализацией длинных списков и количеством одновременно активных графиков/подписок.
- Токен Telegram-бота, серверные API-ключи и другие секреты могут находиться только на backend в переменных окружения. Никогда не добавлять их в клиентский код, README или git.

## Стиль разработки

- Перед изменением прочитать связанные файлы и не затирать пользовательские изменения.
- Для изменений файлов использовать `apply_patch`; не применять разрушительные git-команды без явной команды пользователя.
- После изменения кода запускать соразмерную проверку. Для обычной задачи: `npm run check`.
- Поддерживать ESLint, Prettier и Stylelint в зелёном состоянии.
- Не делать рефакторинг вне текущей задачи без согласования, если он затрагивает много слоёв или поведение.
- В ответе пользователю кратко перечислять изменённые файлы, поведение и результат проверок.

## Работа с внешними источниками

- При работе с меняющимися API, лимитами, лицензиями, документацией бирж и актуальными библиотеками проверять официальные источники.
- Для технических утверждений использовать первичную документацию или исходный репозиторий библиотеки.
- Не передавать данные пользователя внешним сервисам без явного разрешения.

## Агенты

### Performance Code Reviewer

Инструкция агента находится в [.agents/code-review.md](./.agents/code-review.md).

Его роль: senior software engineer, который не меняет код, а проверяет его с приоритетом на скорость работы проекта.

Вызывать ревьюера:

- после значимого изменения графика, API-слоя, WebSocket, сетки графиков или FSD-миграции;
- перед добавлением тяжёлых библиотек;
- перед merge/release крупной функциональности.

Ревьюер обязан проверить P0/P1/P2 риски: повторные запросы, утечки, блокировку main thread, bundle size, кэширование, WebSocket, виртуализацию и границы FSD.

### Рекомендуемые будущие агенты

- **Architecture/FSD reviewer** — проверяет направленность импортов, public API слоёв и декомпозицию на pages/widgets/features/entities.
- **Market-data engineer** — проектирует адаптеры Binance/Bybit/OKX, историю, WebSocket и rate-limit стратегию.
- **Chart & indicators engineer** — отвечает за Lightweight Charts, line-tools, панели индикаторов и производительность сетки.
- **Pattern-research agent** — формализует стратегии в детерминированные условия, готовит тестовые выборки и критерии качества формаций.
- **QA agent** — пишет и поддерживает сценарии проверки: сортировки, график, объекты, сигналы, устойчивость к сбоям API.
- **Security reviewer** — проверяет backend Telegram, секреты, доступы и обработку пользовательских данных.

Не создавать новых агентов ради простой задачи. Делегировать только независимые, ограниченные по объёму подзадачи.
